Security is a stage not a signature

For most of software history, security happened at the end. A team built for six months, handed the result to a review board, and waited. The board found problems late, when they were expensive, and the only lever it had was to say no.

DevSecOps moves that work into the pipeline. Every stage of delivery carries its own security practice, running automatically, giving an answer in minutes instead of weeks. The review board becomes a policy the build must satisfy — and anyone can see, at any moment, exactly which check would stop a release.

Why it changed

The same flaw, found at two different moments.

The old shape

Found in the penetration test, three days before launch

A hardcoded credential sits in the repository for four months. It surfaces in a report, and now a fix means a code change, a rebuild, a re-test, a rotated secret, and a launch date that moves.

Feedback arrives in months. The fix touches work that has been built on top of it many times over.

The DevSecOps shape

Found by a pre-commit hook, ninety seconds after it was typed

A secret scanner refuses the commit. The developer still has the whole change in their head, deletes the line, and moves the value into the secret store. Nothing downstream ever sees it.

Feedback arrives in seconds. The fix touches one line, in one head, once.

Nothing about the vulnerability differs between these two columns. What differs is when the pipeline asked the question — and that alone accounts for most of the cost. This is the whole argument for shifting left, and every stage below is an application of it.

The eight stages

Each one asks a question, and has tooling that answers it.

  1. 1

    Plan Written by people

    Before any code exists, decide what could go wrong. Threat modelling walks the design and asks how an attacker would approach each trust boundary, and security requirements are written into the story rather than bolted on later.

    The question: what are we building, and what would it look like to abuse it?

    PracticesThreat modelling (STRIDE) · abuse cases · data classification · security acceptance criteria
  2. 2

    Code Written by people

    The developer's own machine becomes the first control. Linters, secret scanners and IDE plugins run as the code is typed, so the cheapest possible feedback loop catches the cheapest possible class of mistakes.

    The question: does this change introduce a known-bad pattern or leak a credential?

    Toolingpre-commit hooks · gitleaks · trufflehog · IDE security plugins · signed commits
  3. 3

    Build Enforced by the pipeline

    CI compiles the artifact and, just as importantly, records what went into it. A software bill of materials lists every dependency, and dependency scanning checks that list against known advisories.

    The question: what exactly is in this artifact, and is any of it known to be vulnerable?

    ToolingSCA · SBOM (CycloneDX, SPDX) · syft · Dependabot · reproducible builds
  4. 4

    Test Enforced by the pipeline

    Static analysis reads the source for injection, unsafe deserialisation and weak crypto. Dynamic analysis runs the deployed application and attacks it. The two find different things, which is why mature pipelines run both.

    The question: does the code contain a flaw, and can it be exploited when running?

    ToolingSAST (Semgrep, CodeQL) · DAST (ZAP) · IAST · fuzzing · security unit tests
  5. 5

    Release Enforced by the pipeline

    The artifact is signed and its provenance recorded, so the thing that reaches production can be proven to be the thing that was built and tested. This is the supply-chain link — it is what stops a compromised build server from shipping something no one reviewed.

    The question: can we prove this artifact came from our pipeline, unmodified?

    Toolingcosign / sigstore · SLSA provenance · in-toto attestations · immutable registries
  6. 6

    Deploy Observed in production

    Infrastructure is code, so it is reviewed and scanned like code. At deploy time the cluster verifies the signature again — trusting the pipeline is not the same as verifying at the door — and secrets are injected rather than baked into the image.

    The question: is the environment configured safely, and is this image allowed to run here?

    ToolingIaC scanning (tfsec, Checkov) · admission control (OPA, Kyverno) · Vault · least-privilege IAM
  7. 7

    Operate Observed in production

    Production drifts. Configuration changes by hand, new CVEs are published against images that were clean last week, and permissions accumulate. Operating securely means continuously re-checking what was true at deploy time.

    The question: is what is running still what we approved?

    Toolingruntime scanning · patch automation · configuration drift detection · access reviews
  8. 8

    Monitor Observed in production

    Detection closes the loop. Logs, metrics and runtime alerts feed incident response, and every incident becomes an input to the next planning cycle — a new threat model entry, a new test, a new gate.

    The question: would we notice an attack, and how fast?

    ToolingSIEM · runtime detection (Falco) · audit logging · incident response runbooks

What a gate actually looks like

Policy as code, versioned with the service.

A "security gate" sounds abstract until you see one. Here is the rule from stage 5, written in Rego and evaluated against an image manifest. It denies any layer that cannot be traced to a trusted builder. Note what it is not: there is no severity score to negotiate over, and no meeting. The layer is either traceable or it is not, and the answer arrives in seconds.

# policy/supply-chain/provenance.rego
package pipeline.gates.release

deny contains msg if {
    layer := input.image.layers[_]
    not layer.attestations.slsa_provenance
    msg := sprintf("layer %v has no SLSA provenance", [layer.digest])
}

deny contains msg if {
    builder := input.image.attestations.slsa_provenance.builder.id
    not trusted_builders[builder]
    msg := sprintf("builder %v is not on the trusted list", [builder])
}

Because the policy lives in the repository, changing what "secure enough" means is a pull request — reviewable, attributable, and reversible.

Four things to carry out of this lecture

The tooling changes every few years. These do not.

  • The cost of a flaw is set by when you find it

    Not by its severity, and not by how clever the fix is. Every practice in this lecture exists to move detection earlier, because that single variable dominates everything else.

  • If a control is not automated, it will be skipped

    Under deadline pressure, a manual checklist is the first thing to go. A control that runs in the pipeline runs on the worst day of the release too, which is precisely when it matters.

  • Security owns the guardrails, not the gate

    The security team's job shifts from reviewing every change to building the checks that review every change. Developers keep ownership of their code; they just get told faster when something is wrong.

  • A gate nobody trusts gets disabled

    False positives are not a cosmetic problem — they are how a pipeline loses its authority. A noisy scanner that blocks builds for nothing will be bypassed within a month, and then it protects nothing at all.
